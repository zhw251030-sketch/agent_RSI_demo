# measured-v02 第七请求：单次提交与 finish 的边界

这是一份离线诊断，不是后继修复，也没有恢复真实实验。真实第七请求同时返回 `submit_candidate` 和 `finish`，只有一份业务候选。当前 `BoundedPilotLLM` 要求整个响应恰有一个工具调用，因此在 SDK 分发和业务字段校验前以 `PilotResponseContractError` 拒绝。它与前一轮已修复的可选元数据不一致是两个问题。

`measured-v02-call-contract-replay.py` 在阻断 socket 网络的条件下，用实际 OpenHands SDK 1.55.1 和假 provider 做了两次回放：

1. 原样保存响应：重现相同错误，没有候选接受。
2. 仅移除末尾 `finish`，业务参数一个字节也不改：得到一次隔离的模拟候选接受。源码仅写入本诊断的 tmp 目录，没有执行、拟合或评分。

两次 SDK 序列化请求文件均与真实第七请求逐字节相同，SHA256 为 `37e44e0933ae108588f57cea7e58f29e2c20dd6cc4b7bb5e196f9e6d376d2c40`。模拟账本沿用保存响应的用量作为测试输入，不能累计为新的研究费用、模型请求或研究候选。报告同时核对 measured-v02 目录内 230 个原文件、256 个冻结运行文件，回放前后哈希均不变；目录外 180 个任务反馈原文件由主验收单独核对，总原档为 410 份。

安装的 SDK 明确提供 `include_default_tools=[]`。另一次无 provider 的独立请求捕获确认该选项让工具表只包含 `submit_candidate`，账本请求为零。源码证据保存于 traces 中的 `installed-sdk-evidence.json`：`agent/base.py:163` 声明禁用默认工具，`agent/agent.py:242` 则表明 SDK 会丢弃第一个 finish 之后的调用。

因此，后续最小且容易审计的方案是让单步提交会话只公布业务工具，统一提示、工具允许表、请求绑定和审计中的工具集合，并继续拒绝多业务提交。现有提示要求提交一次业务工具，却同时公布 finish，也未明确禁止同响应的结束调用。只把调用数限制放宽到二是不充分的；若选择兼容“业务提交后 finish”，必须先完整验证两项原始参数、唯一调用身份、顺序和没有额外调用，再允许任何接受，并相应审计两项事件。这个替代方案本次没有实施或验证。

当前 24 份诊断 trace、报告及脚本均为离线证据；不把模拟接受追认为 measured-v02 第七请求的真实接受，不追加下游测量。
