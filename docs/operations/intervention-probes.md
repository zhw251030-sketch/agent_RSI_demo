# 可执行干预校准：做了什么，为什么做

这一轮要补上一个具体环节：当 Agent 说“这样改就能修好”或“新增这一项没有价值”时，我们怎样用一次范围明确的干预，检查这句话，再决定允许做什么修改。我们先校准检查工具，模型调用计划为 0；候选程序和公式仍由既有隔离执行器运行。

本轮已经完成：**规划的格式干预在两个公开题上均足以修复当前计划，严格格式补丁的新程序通过10/10开发题；两次符号删项得到了不同的局部判断。** 共22次任务级评价、28次sandbox调用，0次新增模型调用。本机与服务器的记录一致性审计均通过。它属于已见开发案例上的研究者干预校准，尚不是Agent自主改进实验。

运行日期2026-10-21，代码提交 `b1f4f81752fc9a162a030c4055a24f80f43733c4`，服务器相对运行目录 `runs/intervention-probes/20261021-intervention-probes-v01`。先看[逐项结果与边界](../analysis/2026-10-21-intervention-results.md)，原始证据见[完整归档](../../artifacts/intervention-probes/2026-10-21/v01/README.md)。

## 1. 为什么现在做有范围的干预

[上一轮说明](inference-policy.md)已经把几件容易混淆的事拆开：源码改变、分数提高、登记预测达成、解释成立、任务成功。检查事实和标签可以发现一部分错误，但仅凭“引用正确”仍然无法知道接下来该怎样修改。

例如，看到规划程序因动作格式被拒绝，可以提出“去掉多余空白就足够了”。但这份计划也可能有方向错误、缺少动作或不满足前提。看到一个公式新增高阶项后训练误差略降，也不能直接说该项必不可少，或者因为降幅小就断言没有作用。我们需要把这些宽泛解释改写成可执行的局部问题。

本轮的共同流程是：

**明确对象和命题 → 只实施指定变换 → 用原评分流程检查结果 → 输出有范围的下一步编辑建议。**

这里“有范围”包括对象、任务、变换和结论四个方面。它要说明究竟检查哪份源码或哪次生成的计划，允许改哪里，用什么数据判定，以及结果最多能支持什么决定。`supported` 只支持这条局部命题，不能升级成整段解释正确或某条通用经验已经有效。

正式范围和停止条件见[冻结协议](../protocols/2026-10-21-intervention-probes-v0.1.md)，具体参数见[配置](../../configs/pilots/intervention-probes-v0.1.json)。案例与阈值是在研究者看过历史开发结果之后选定的，因此本轮不作为独立确认或盲测。

## 2. 规划：先检验同一份计划，再考虑修改生成程序

规划侧检验的命题是：

> 对本次在指定公开题生成的失败计划，仅规范化动作括号内外边缘的 ASCII 空白，就足以完成该题。

这句话检查的是具体计划的格式干预，不是“原规划算法没有其它问题”。允许的变换非常窄。例如，`( walk shed gate bob )` 可以变为 `(walk shed gate bob)`；动作名称、大小写、参数、动作顺序、动作数以及 token 之间原有空白都不改变。不能为了通过验证补动作、交换方向或删掉失败步骤。

旧归档没有保存完整 plan，所以本轮需要把已固定的旧源码放回原 sandbox，在一个公开题上新增执行一次，取得并保存完整计划。**这不是重放一份已经归档的历史完整计划**，也不会回填旧成绩。取得计划后，才在宿主侧从同一个结果生成原始版和规范化版。这保证比较的两边共享同一次搜索结果，避免两次程序执行碰巧产生不同路线。

[planning_probe.py](../../rsi_eval/planning_probe.py)让原始版和规范化版分别经过既有 [planning.py](../../rsi_eval/planning.py) 与 [planning_diagnostics.py](../../rsi_eval/planning_diagnostics.py)。前者执行宿主格式与对象检查，并在适用时调用 VAL；后者独立回放公开题的 STRIPS 状态变化。VAL 与回放的成功／失败结论必须相容。

需要特别区分：当宿主接口先因 `operator_syntax` 拒绝动作时，VAL 根本还没有被调用。这样的记录只能说明冻结的任务接口不接受原输出，不能写成“VAL 原生语法不允许这种写法”。本轮不放宽评分接口，而是把候选输出变换后重新走同一套接口。

| 同一份计划的观测 | 返回判断 | 可以据此做什么 |
|---|---|---|
| 原始失败，规范化后成功 | supported | 考虑严格限定的格式修复 |
| 原始失败，规范化后仍失败 | contradicted | 格式处理不足以修好，应检查剩余语义问题 |
| 原始已经成功 | unknown，原命题不适用 | 不把已经成功的计划算作修复成功 |
| 无法安全识别单一动作或没有可用计划 | unknown，给出具体原因 | 暂不据此决定修改 |
| 验证器故障、数据异常、VAL 与回放冲突 | infrastructure_error | 停止本轮，保留记录，不作候选质量结论 |

我们固定了三个历史源码作为校准案例：括号内多余空格的案例、返回空计划的控制、原已成功的控制。三个案例都只使用原公开的 problem0 和 problem1。空计划可以检验工具会不会把“格式本来就合法”误当作“任务已完成”；原已成功的控制可以检验工具会不会对不适用的修复命题也给出支持。不能根据本轮结果另换更好看的案例。

只有第一个案例在两个公开题上都得到 supported，运行器才允许进入下一层：生成一个新的程序源码，把唯一 `_fmt(name, params)` 中精确匹配的冗余空格表达式改掉。函数可以嵌套，但只替换其指定 return 的字节区间，保留嵌套位置与区间外源码，并静态验证其它 AST 相同。这里 AST 指 Python 语法树，证明的是修改范围，没有证明整个程序正确。

随后新程序在原来的 2 个提示题和 8 个开发题上重新执行。它可能搜索出不同计划，因此要把两种证据分别报告：

- **同 plan 干预**说明，这一次已生成的计划是否只差格式处理。
- **新程序评价**说明，限定的代码改动后，程序在原 10 题上的实际行为怎样。

前者成功不自动保证后者十题成功；后者十题成功也不证明对新问题分布泛化。这份源码修复由研究者预先指定的契约生成，不是模型主动发现并完成的修复。

## 3. 符号：用 sham 排除转换影响，再检查删项的训练代价

符号侧把“这个结构是否必要”缩窄为：

> 删除指定新增项，并按同一协议重新拟合，会不会让 oscillator1/train 的 NMSE 增加超过 ε？

固定两个历史转换：一个删除新增的 v³ 项，参数维度从 6 降为 5；另一个删除新增的 x⁵ 项，参数维度从 5 降为 4。具体对象、源码 hash 和父子谱系由 [probe_cases.py](../../rsi_eval/probe_cases.py)固定，不能把其它公式的分数拼过来。

[symbolic_probe.py](../../rsi_eval/symbolic_probe.py)先在宿主侧静态检查窄公式语言：每个加法项只有一个独立系数，参数编号明确，剩余各项经过别名展开和参数重编号后，与父式结构及顺序一致。这里“独立系数”表示每个参数只属于一个项，不表示 x、v 或不同基函数在统计上独立。存在系数耦合、动态索引或不支持的代码结构时，工具返回 unknown，不猜测如何删项。

删除一个项后，参数向量也真正减少一维，剩余参数重新编号。它不是暂时把系数设成 0 后仍让拟合器使用原来的自由度。宿主只解析和生成受限 AST；所有公式求值仍发生在隔离进程内。

每个案例都重新拟合三份源码：

| 版本 | 内容 | 用途 |
|---|---|---|
| original | 归档完整原式 | 取得本轮相同配置下的参照 |
| canonical_full | 转换后的完整式，仍保留指定项 | sham 对照：检查规范化转换本身是否带来分数漂移 |
| removed | 同一规范化表示，删除指定项并降低维度 | 测量删项后的训练拟合损失 |

sham 在这里是“经过同一套表达式转换，但不删项”的对照。展开别名、整理加减乘表达式可能改变浮点运算顺序，进而影响数值拟合。因此，即使表达式在数学上相当，也先核对原式与完整 sham 的 NMSE 差是否不超过 `1e-10`。超过该容差就停止此案例并记 unknown，不把转换引起的差异归因于删除项。

三版使用同一份哈希验证的 oscillator1 训练文件、全 1 参数初值、固定的 `least_squares(max_nfev=100)`。拟合与预测分别在新的隔离进程中完成，最终分数由宿主计算。旧历史分数只作背景，不拿来替代本轮重拟合的原式对照。拟合不收敛、来源或参数维度不一致、非有限分数等，都不能形成删项结论。

具体比较量为：

`Δ = NMSE(removed) − NMSE(canonical_full)`

本轮工程阈值为 `ε = 1e-5`，比较容差为 `τ = 1e-10`。NMSE 越低越好，两者都以 NMSE 的量纲解释，不与历史 MSE 预测阈值混用。

- `Δ > ε + τ`：supported，删除该项的训练损失超过指定阈值。
- `Δ < ε − τ` 且没有明显负向异常：contradicted，当前协议不支持“删项损失超过阈值”。
- 落在阈值边界：unknown，避免把数值边缘差异当作确定判断。
- `Δ < −τ`：unknown。删项后的嵌套模型反而明显更好，先标记拟合或匹配疑虑，不直接解释成该结构有害。

ε 是研究者看过历史开发误差后选择的工程效果阈值，不是 p 值阈值，也不产生统计显著性结论。supported 最多说明“在这份训练数据、这次固定拟合协议及该阈值下，保留该项有局部依据”；contradicted 最多允许考虑已经实测过的简化候选。两者都不证明物理必要性、最优方程或独立数据上的预测能力。

另有一份研究者构造的系数耦合公式，只用于检查“不支持的转换应返回 unknown”。它不执行候选，也不算 benchmark 或模型生成结果。

## 4. 输出为什么要包含“下一编辑范围”

本轮的报告不只给一个标签，还由运行器生成 `next_edit_scope`，把标签和允许讨论的下一步关联起来：

| 任务与判断 | 下一步编辑范围 | 证据边界 |
|---|---|---|
| 规划 supported | 考虑符合 AST 契约的格式补丁 | 先限于本次公开题计划；新程序另行评价 |
| 规划 contradicted | 检查剩余语义问题 | 只知道格式处理不足，尚未定位其它唯一原因 |
| 符号 supported | 在固定训练协议下保留指定项 | 不延伸为物理上必需 |
| 符号 contradicted | 考虑已实测的删项式 | 不直接宣布它是最优或泛化更好 |
| 任一 unknown | 暂不作相应编辑推断 | 保存缺失证据或不适用原因 |

这是一个确定性的范围映射，不是已经学习出来的策略。它的作用是避免把“局部检查支持”直接扩大成任意改代码、任意删结构的许可证。除冻结的规划补丁分支外，本轮不会根据标签再启动新的模型修订循环。

按冻结设计，最多为 6 次公开规划生成、10 次条件触发的修复程序评价、6 次符号公式评价，共最多 22 次任务级评价、28 次候选 sandbox 调用；硬上限 40。符号一次评价包含 fit 与 predict 两个隔离进程。单元测试与研究执行分别计数，宿主格式拒绝不能计成一次 VAL 调用。发生无法精确核对的异常时保留不完整标记，不把已知计数下界写成精确总数。

第一例两个公开题都满足触发条件后，我们按AST契约生成新程序：仅替换 `_fmt` 的return字节区间，其它字节及AST不变。该新程序在原2提示+8开发题全部成功。原模型生成程序的历史0/10成绩原样保留，这次10/10属于研究者受控源码干预，不记为模型成功生成或学习到的收益。同plan干预提供两题的格式充分性证据，新程序的10题结果提供修复后执行证据。

两次符号比较都使用完整原式、完整规范式和删项式重新拟合；NMSE越低越好。

| 指定干预 | 原式NMSE | 完整规范式NMSE | 删项式NMSE | 删项损失Δ | 对“损失超过1e-5”的判定 |
|---|---:|---:|---:|---:|---|
| 删除v³项，6→5参数 | 0.092249034101 | 0.092249034101 | 0.093762299670 | 0.001513265569 | supported |
| 删除x⁵项，5→4参数 | 0.091803987228 | 0.091803987228 | 0.091804705248 | 0.000000718020 | contradicted |

两个sham差分别为0和1.3878×10⁻¹⁷，均低于数值容差1e-10；因此这两例没有观察到代码规范化引起的实质评分漂移。v³项在当前训练拟合中的贡献超过工程阈值，支持局部保留；x⁵项仍有微小训练收益，但删去它的损失低于阈值，允许考虑已经执行过的更简公式。后一结论不等于“这个项无用”，两者都不判断物理真实或泛化能力。

人工系数耦合公式在静态转换阶段返回unknown，原因为 `term_requires_one_independent_coefficient`，候选执行为0。这为拒绝不适用干预提供了一个明确的测试例；它不是第三个真实符号任务。

实际计数：6次公开规划生成+10次格式补丁评价+6次符号评价=22次任务级评价；其中符号评价分fit/predict，因此总sandbox调用28次。宿主规划验证22次，实际VAL20次，6次fit与6次predict。两个原格式失败被宿主预检拒绝，未调用VAL。预算预留28/40，无重试或恢复。模型调用、封存评价均为0。

运行前服务器610项收集测试中538项通过、72项SDK测试跳过；本轮不改变SDK或模型接口，因此没有为了凑总数重跑SDK。最终本机73项新增针对性测试通过。服务器已有SciPy完成全任务验收；本机完整发现曾因缺少SciPy及仍在TDD阶段的审计模块而不能通过，未将这次中间检查算作成功。源码审查还修复了父候选/策略绑定、提前失败时的验证计数以及Python3.10/3.12空type_params字段导致的静态证明哈希差异，均在真实研究执行前完成。

事后21项审计回归在本机和服务器均通过，其中12类临时副本篡改全部被拒绝，原件哈希保持一致。31份服务器运行原文件逐字节归档；另加manifest与阅读说明。来源、变体、差值、标签、执行计数与运行Git文件绑定通过[审计](../analysis/2026-10-21-intervention-audit.json)，详细验收记录见[核验文件](../environment/2026-10-21-intervention-verification.json)。这些审计核对受信执行记录，不独立重跑VAL或从原始预测重算NMSE。

## 7. 这一步怎样连接未来的固定权重 Agent 改进机制

本轮完成后，能够得到的是两类检查接口的校准证据，以及它们怎样约束下一步编辑的具体案例。Agent 自主提出假设、选择检查、利用检查调整行为、从多次经历更新持久策略，仍然需要另一个实验。

下一步应先接入受控OpenHands的两阶段流程，并以相同模型/工具预算检验检查结果是否改善实际修订。当前每类任务只有一种干预，尚不足以实验评价“自适应选择哪种检查”；若进一步研究选择机制，需先为同一类任务提供多个有区分力的候选检查。后续可围绕同一机制设计：Agent 先提出范围明确的修复假设，在固定成本下选择一个有区分力的检查；检查返回局部证据和未知原因；Agent 再决定修改什么，并把经过验证的适用条件记入经验。基础模型权重保持固定，可变的是外部检查选择和经验使用方式。规划与符号任务的共通之处是这一决策流程，而不是强迫两边使用同一种格式补丁或删项操作。

要检验这个机制，仍需比较调用次数、工具预算和输出预算匹配的条件，例如固定检查与按证据选择检查；保留相同起点，并使用未参与当前工具设计的新状态。既要看结论判断是否合适，也要看下一次实际修改是否更好，不能只统计模型是否复述了工具标签。具体正式比较、统计单位和独立验证范围仍待冻结。

因此，本轮可以称为“可执行干预工具与编辑范围的离线校准”。即使局部补丁成功或删项给出明确结果，也还不能写成“Agent 已学会自我改进”或“形成了普适 RSI 算法”。本轮所有干预对象、选择规则和执行顺序都由研究者事先确定。
