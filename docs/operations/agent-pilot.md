# 受控 Agent 小试：实现、使用与结果解读

更新日期：2026-10-20。本文件解释从“手写候选能够执行”到“模型能够提出候选并读取反馈”的新增部分。文末结果来自服务器真实运行报告；原始运行与恢复记录均保留。

本次小试使用 MiniMax-M3、OpenHands SDK 1.55.1 和已有任务执行器，保持基础模型权重与修订提示不变。它首先检查一次完整的交互是否成立：模型拿到任务及起点，提交程序或公式，收到真实评价反馈，然后修改或结束。它不同时引入新的策略更新算法。

## 为什么固定初始产物 P 和修订策略 S

这里的 P 是实际执行的程序或公式；S 是指导模型如何利用反馈修改 P 的文字规则。本轮只让 P 变化，S 固定为 `fixed-revision-v0.1`：区分反馈事实与假说、提出有理由的一次修改、执行、读取反馈并按固定规则保留或退回。

规划的初始 P 是返回空列表的程序，符号的初始 P 是只有一个待拟合常数的表达式。它们是明确、可审计的简单起点，不是具有竞争力的成熟算法。runner 会检查其文件哈希，先获得真实的起点评价，再把源代码和反馈交给模型。模型提出的候选不能冒充初始样例，初始样例也不能冒充模型发现。

这样安排是为了先分清两件事：模型能否修好一个当前产物，以及修订策略本身有没有变好。本轮最多能观察前者。以后要研究 S 的改进，需要在同一起点、同等预算下比较旧／新策略，还要让策略在未用于选择的新父产物上工作；仅保存本轮最好的成品无法回答这个问题。

## 两条路线实际给模型什么、要求它返回什么

规划会话公开 Spanner 动作规则和 seed0 的两道 prompt 示例。每个实例包含带类型的对象、初始事实和目标事实；候选函数接收 `objects`、`init`、`goal` 三个集合，集合元素都是 tuple。模型提交完整的 `get_plan(objects, init, goal)` Python 源码，返回形如 `(walk 起点 终点 人)` 的动作字符串列表。

同一个候选依次运行在两道 prompt 和八道 development 实例上，总计十题。外层检查动作格式、类型及 VAL 的合法性与目标达成结果。两道 prompt 的具体输入可以出现在模型提示中；另外八道题提供逐题开发反馈，完整输入不附加给模型。十题都属于本轮开发用途，不能将其中的八题称为独立测试集。封存测试仍不执行。

符号会话先使用 oscillator1：输入位置 x、速度 v，输出加速度 a。模型提交 `equation(x, v, params)` 的完整 Python 源码及参数数量。NumPy 数组运算可用，返回值必须是一维、长度与输入一致的有限数值数组；参数数量必须在 0 到 16 之间。

外层只加载官方 train，调度隔离进程拟合公式中的常数并校验返回参数，再在新的受限进程中只提供输入和拟合常数进行预测，最后由外层计算 MSE／NMSE。模型收到训练评分，不收到真实方程、原始样本行或数据路径。拟合与评分目前使用同一批训练观测，因此误差下降只支持“训练拟合改善”。本轮未调用 test_id、test_ood；oscillator2 留待后续，并未取消符号路线。

```text
固定公开任务、初始 P、固定 S
                ↓
         MiniMax-M3 提出 P'
                ↓
   submit_candidate(source, n_params, rationale)
                ↓
   固定任务批次 → 隔离执行 → 外层可信评价
                ↓
   保存所有候选和反馈 → 按固定规则选 incumbent
                ↓
      返回所选起点 → 下一次修改或结束
```

模型的 `rationale` 是修改理由或原因猜想，单独保存。它不能覆盖验证器结果，也不自动成为“已证明的错误原因”。当前规划语义失败反馈较粗，只说明某个前置条件或最终目标不满足，不包含完整状态轨迹；这种反馈是否足以支持修订，是小试可以观察的实际问题之一。

## 如何选候选，以及为什么同时看 first、last 和 best

规划先比较八道 development 成功数，再比较两道 prompt 成功数；完全相同时保留更早候选。符号选择成功且有限的最低 train NMSE；完全相同时同样保留更早候选。无效或失败的符号候选不能替换成功候选，基础设施异常也不能作为正常能力分数参与选择。

下一次修订从当前被选中的 incumbent 出发。每次反馈包含选择决定和 incumbent 身份／源码；如果刚提出的候选变差，下一次的 parent_id 指向保留下来的较好候选，而非机械地指向最后一次提交。

报告分别保存以下位置，它们不一定是同一个候选：

| 位置 | 含义 | 主要作用 |
|---|---|---|
| `baseline`／initial | 固定手写起点 | 交代模型实际从哪里开始 |
| `first` | 第一个模型候选 | 观察首次改写的作用 |
| `last` | 最后一个模型候选 | 保留后续修改可能退步的事实 |
| `best` | 根据开发规则选中的最佳候选，可能仍是初始候选 | 记录有限搜索后的开发选择结果 |

没有模型候选时，first 和 last 必须为 null。最佳成绩经过选择，不能直接当作独立测试成绩。全部候选源码、拒绝、失败和中间反馈都保留，不能只展示最好的一个公式或程序。

## 请求额度、候选额度和预算分别是什么

| 上限 | 当前配置 | 如何理解 |
|---|---:|---|
| 每会话模型候选 | 3 个 | 初始手写样例额外评价；重复源码也占生成候选额度 |
| 每会话模型请求 | 4 次 | 包括终结回复、失败与恢复请求，不能保证一定得到三个候选 |
| 两会话模型请求合计 | 8 次 | 规划与符号共享同一本总预算账本 |
| 单次输出 | 4096 token | 发给供应商的输出上限 |
| 单次序列化输入 | 96 KiB | 发出请求前检查任务、历史与工具描述的体积 |
| 小试累计保守计量预留 | 800000 | 预留单位使用输入 JSON 的 UTF-8 字节数加余量等构造，不是供应商实测 token |
| 本地费用预留 | 5 元 | 包含在用户此前 300 元总预算内；不是供应商账户硬限额或已支付账单 |

`pilot_budget.py` 在网络发送前把预留写入账本，并使用互斥锁与原子替换，防止并行或中断使额度丢失。输入预留采用紧凑 JSON 的 UTF-8 字节数加 8192 的余量；实际返回的 token 使用量另记。预留不退还，失败请求也保留。若供应商 usage 缺失或实际使用量超出预留，后续请求停止并标记原因。

成本预留采用配置中的标准输入 2.1 元／百万 token、输出 8.4 元／百万 token，来源见 [MiniMax 官方价格说明](https://platform.minimax.cn/docs/pricing/overview)。缓存等细项和实际账单需要另行核对；只要有请求使用量未知，报告就不能给出一个假装完整的“实际总费用”。

候选执行次数与模型请求次数分开统计。无恢复时，初始加三个生成候选最多对应 40 次规划实例评价和 4 次符号拟合／预测评价；两者并不是 44 次模型请求。显式恢复会在新的目录重新检查固定起点，其额外执行需要在跨运行汇总中保留，不能只计算恢复目录的工作量。

## 如何准备、运行和查看记录

以下命令在服务器项目目录执行，使用本项目 `.venv`。先使用独立且未存在的 run ID 做预备检查：

```bash
.venv/bin/python scripts/run_agent_pilot.py --prepare-only --run-id pilot-precheck-example
```

`--prepare-only` 会校验配置与固定起点、实际评价两个初始候选并生成任务提示；它不调用模型，也不读取模型密钥。它不是形式上的空转：规划和符号执行器都会被实际使用。

真实执行需要显式选 `--execute`，脚本才会读取服务器上已有的模型配置和授权凭据：

```bash
.venv/bin/python scripts/run_agent_pilot.py --execute --run-id pilot-execution-example
```

这些命令是入口说明，不表示应重复启动已经完成的小试。每次执行目录必须新建，脚本不覆盖已有结果。输出位于 `runs/agent-pilot/<run-id>/`，原始运行目录受 Git 忽略，不随代码上传。

| 记录 | 包含什么 |
|---|---|
| `summary.json`、`config.json` | 运行模式、状态、实际配置、源码／提示哈希、代码提交、两个会话概要 |
| `budget-ledger.json` | 每次请求的预留、使用量、失败状态和停止原因；恢复时继续使用原运行账本 |
| `<session>/task-prompt.txt` | 本次真正交给模型的公开任务包与固定起点反馈 |
| `<session>/candidates/*.py`、`candidates.json` | 全部候选源码、父候选、修改理由、每题反馈与选择决定 |
| `<session>/requests/` | 经过约束的请求／响应记录；不保存认证字段或原始供应商异常正文 |
| `<session>/events.jsonl`、`session-summary.json` | SDK 事件类别、工具身份、结束状态和候选汇总 |

研究会话明确只允许 `submit_candidate` 和 `finish`。启动时关闭隐式插件、项目／用户上下文、MCP、外部工具和多工具并发，实际工具集合不匹配就拒绝运行。相关适配针对已固定的 SDK 1.55.1；它不改变现有通用 Canvas 会话。

## 设施失败后的有限恢复

若供应商报错、没有使用量、也没有返回模型候选，默认停止。协议补充允许操作者显式恢复一次：用新运行目录，复用旧 ledger，保留已占请求额度与所有预留，不更换模型、提示、任务、起点或选择规则。

恢复入口是 `--execute --resume-from <原run-id> --run-id <新run-id>`。脚本检查原运行身份、配置哈希、无生成候选的条件与账本中的失败类型；账本还检查没有已经使用过的恢复记录。再次发生未知使用量的供应商错误则停止，不进行第二次恢复或自动重试。

该恢复规则在首次设施错误后单独补充，原协议和失败记录保留。没有返回候选不能算修订收益，也不能从请求计数中删除。若已经获得候选，则不能以成绩不佳为由使用这条规则重跑。

## 真实运行结果与当前结论

**模型已在两条路线各提出三个候选，符号会话正常结束；规划会话在达到请求预算后停止，三个规划候选均未解决开发题。** 因此整个运行的准确状态是 `completed_with_stops`，不能写成“两任务都成功完成”。

原运行 `20261020-minimax-v01` 使用代码 `240ad8099ea9a1f63a70f1b3069e9e4742d37d09`。其第一个规划请求遇到供应商 `InternalServerError`，没有 usage，也没有产生候选；预算账本随后停止符号会话启动。已完成的两个固定起点评价和失败请求记录保留。

显式恢复运行 `20261020-minimax-v01-recovery` 使用代码 `49b4b9f6d967360b264cd93f52c326a7814bb595`，继续使用原运行的预算 ledger。恢复后规划成功接收三次模型响应、评价三个候选；它再尝试取得终结回复时，在网络发送前因规划已占四次请求额度而被 `BudgetExceeded` 拒绝，没有第五次规划付费请求。符号接收三次候选响应及一次 `finish` 响应，正常结束。
