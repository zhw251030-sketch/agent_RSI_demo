# 可执行证据检查：本轮实现、真实运行与结论边界

日期：2026-10-20（Asia/Shanghai）。阅读顺序：本页 → [v0.2 逐条分析](../analysis/2026-10-20-checked-feedback-v02-analysis.md) → [完整候选与响应](../../artifacts/checked-feedback/2026-10-20/v02/README.md)。

本轮完成了全请求长度控制、可执行主张检查、事前预测登记，以及四个条件的有界真实尝试。检查器已在两类任务上运行；**反馈是否改善修订能力仍未得到完整有效的对照证据**。其中符号隐藏组没有执行候选，规划两组实际执行候选数不同；规划检查组第一次成功提交便达到10/10，发生在收到候选检查反馈之前。

## 1. 为什么先做这一步

上一轮的两个问题直接影响研究判断：历史工具反馈不断累积，第四次请求在发送前超过96KiB上限；模型虽然会引用证据，但仍可能把动作规则改写、把弱关联说成必要结构，或把分数量级解释错。因此本轮先把“说得像有依据”变成一部分机器可判定的声明，再观察它如何参与下一次修改。

共同流程是：固定任务和当前产物 → Agent提交新程序/公式、1–2项证据主张和一项改进预测 → 控制器先绑定并登记声明 → 隔离执行候选 → 外层评分 → 核对预测 → 下一次修订。基础模型权重、评分规则和会话内修订策略S均固定；当前修改的是产物P。

这只是机制的可执行原型。采用工具反馈和迭代修订已有CRITIC等先例，不能因增加检查器就声称全新方法；论文来源及比较边界见[初版协议](../protocols/2026-10-20-checked-feedback.md)。

## 2. 具体文件做了什么

| 文件 | 负责的工作 | 为什么需要 |
|---|---|---|
| [state_packet.py](../../rsi_eval/state_packet.py) | 用固定任务、当前最佳源码、近期可信诊断、完整候选分数历史和有限检查记录，替换所有非system/developer历史消息 | 控制整个下一次请求的长度，同时保留修改依据；旧源码和原始反馈仍在磁盘归档 |
| [checked_agent.py](../../rsi_eval/checked_agent.py) | 发布声明工具schema，按SDK实际外层参数规则核查；发送前记录整个请求字节数/哈希，精确标记拒绝原因 | 工具定义和系统消息也占输入预算，不能只截断某个工具返回值 |
| [evidence_checks.py](../../rsi_eval/evidence_checks.py) | 核对数值比较、PDDL原子是否存在、改动后指标是否达到事前预测 | 将可判定的事实和量级从自然语言理由中分离，拒绝猜测或事后改写声明 |
| [checked_controller.py](../../rsi_eval/checked_controller.py) | 将两种任务的可信反馈映射成统一证据对象，先登记再执行，按真实子候选核对预测 | 相同的检查规则适用于两种输出，但任务专属解析仍由适配器负责 |
| [run_checked_feedback.py](../../scripts/run_checked_feedback.py) | 固定四组顺序、共同起点、模型与预算，持久保存请求/候选/检查/费用 | 在有限成本下探索显示检查结果的作用，保留失败与缺失条件 |
| [replay_checked_history.py](../../scripts/replay_checked_history.py) | 离线重建上一轮的SDK请求并核对旧文件未改 | 不付费、不重跑候选，先检验输入控制是否解决已知超限问题 |

状态包上限64KiB，完整请求上限仍为98,304字节。旧规划B的四次输入经新接口离线重建为24,866、31,876、33,562、35,355字节；v0.2实际13次请求最大36,996字节。两者都低于原上限，未通过提高上限掩盖问题。原始日志仍保留，但模型每步不再能重读所有旧源码；这也是压缩的真实代价。离线重放复用旧候选及反馈；新声明、预测和usage是人工测试夹具，仅检验SDK兼容与输入长度，不能视为旧模型生成的声明或新实验测量。

## 3. 检查器究竟能检查什么

每项证据引用绑定会话、候选ID、源码SHA-256、任务、证据版本、数据范围和字段。旧候选的数值不能自动当成新候选的数值，同名ID也不能跨会话混用。

支持的例子包括：某候选的训练NMSE是否小于0.1；PDDL动作的负效果是否包含指定原子；新候选相对指定父候选是否至少降低0.005 NMSE。检查结果为supported、contradicted、unavailable或schema_invalid。数值比较有明确容差；缺少证据、设施评价不完整和格式错误不会被自动判真。

预测在执行前登记。例如模型事前声明“加二次项后NMSE至少下降0.005”，实测只下降0.00054804，就记录contradicted；即使这个候选分数略好并被采纳，也不能把该预测改判成功。

**supported只支持声明中的精确谓词。** 它不证明整段理由正确、不证明因果解释、不证明这个改动必要，也不保证公式恢复真实物理规律。当前检查不会解析全部自然语言，因此它不能自动捕获所有解释错误。声明检查也不决定候选是否运行或被选中；候选选择继续依据原评分规则。

## 4. 实际怎么比较

固定MiniMax-M3、OpenHands SDK1.55.1、同一声明格式和共同弱起点。规划使用Spanner seed0的2个提示题+8个开发题，符号使用LLM-SR公开原始任务oscillator1/train的10,000行。它们都是已用于开发的范围；本轮没有读取或评分封存集。

每类任务分hidden与checked：两组都提交声明、接受同样执行反馈，控制器都计算检查；checked把检查结果提供给下一次请求，hidden只在日志保存。每会话最多4次模型请求、3个实际候选。格式错误也消耗请求额度，不临时补次数。公开的声明结构和任务信息一致，但检查结果会自然改变后续输入长度。

| v0.2条件 | 实际模型请求 | 实际执行的新候选 | 开发结果 | 必须同时看到的限制 |
|---|---:|---:|---|---|
| planning_hidden | 4 | 1 | 0/10 | 前3次提交格式错误；最后候选动作语法错误；SDK达到迭代上限 |
| symbolic_checked | 4 | 3 | train NMSE：1 → 0.09694021 → 0.09639217 → 0.09505566 | 三个候选均被采纳，但仍只是训练拟合 |
| planning_checked | 4 | 2 | 第一个、第二个均10/10 | 第一份有效提交已满分，不能把该提升归因于检查反馈；并列保留第一份 |
| symbolic_hidden | 1 | 0 | **无有效候选结果** | 响应标记tool_calls却没有实际tool_calls，SDK将文字消息当成结束；起点NMSE1不是该条件的方法成绩 |

新生成候选共6个，加4个固定起点共10份源码；共50次规划实例评价和5次符号拟合。12项正式主张中8项supported、4项schema_invalid；6项预测均成功登记，4项supported、2项contradicted。其中规划第二次“增加至少0”只表示不下降，不能算性能提升。

原始runner状态为completed_with_stops；其中symbolic_hidden的旧会话状态甚至为completed。报告依据真实工具执行和候选记录解释这些状态，不改写旧日志，也不把状态字符串当作实验完成证据。

## 5. 本轮暴露的问题和处理

先运行的v0.1在8次请求后人工停止：额外格式审查没有正确处理SDK自带的summary/security_risk字段，造成有效提交被误标；模型收到的声明schema也过于宽泛。修复后另建v0.2、另开账本，完整保存v0.1失败，不混为同一比较。见[v0.1事件记录](../analysis/2026-10-20-checked-feedback-v01-incident.md)与[v0.2事前协议](../protocols/2026-10-20-checked-feedback-v0.2.md)。

v0.2仍有格式不稳定：规划返回中出现额外业务字段和碎片化声明。离线核查表明SDK发布和LiteLLM请求转换中的嵌套schema完整；畸形参数在观察器处理前的响应中已存在。由于未保存原始HTTP响应，不能进一步断言是模型生成还是上游兼容层解析导致。成功的嵌套输出也说明并非一概不支持该格式。

符号隐藏组的“结束但无候选”另做事后离线边界修复，见[工具响应契约审查](../analysis/2026-10-20-tool-response-contract.md)：遇到标称tool_calls却缺少实际调用的响应，明确记录契约错误，保留已知费用与原响应，不从文字里猜出代码执行。此修复不追溯改写v0.2，不追加第三轮付费请求。

更值得研究的是解释仍会失真。符号检查组曾将x²称为奇函数；对prediction−target残差的方向解释反了；最终总结还把不同候选的公式身份和父/子证据混用。这些错误与部分数值声明为真可以同时发生。逐项证据和真实源码见[v0.2分析](../analysis/2026-10-20-checked-feedback-v02-analysis.md)。

## 7. 下一步的研究安排

先稳定接口并降低无关的抄写负担：由可信控制器给证据分配短ID，精确映射原有完整绑定；用本轮成功和失败响应做离线兼容回放，再决定是否另开小规模接口探针。JSON字符串承载也是候选，但其转义和严格解析负担尚未验证，不能先宣称更可靠。

机制实验应从“同一批固定修订状态”起步，把产物质量、有效工具提交率、主张覆盖率、预测校准和额外成本分别衡量。对相同父产物/诊断配对检查可见性，尤其区分第一份解已经成功与收到检查后才改进；预先明确格式失败计入总体性能的方式，并保证两组公平的请求预算。随后才研究检查记录怎样更新S，并在未参与提示设计的新状态及另一类任务上验证。

这一步收获是可执行基础和具体可复核的失败现象；完整机制收益、跨任务泛化、策略S更新与长期博士贡献仍待后续实验。
