# 新起点批次与超时边界核查

本轮承接[第一批中止记录](state-generation.md)，目标是取得完整的新起点来源；结果与费用见[本批结果报告](../analysis/2026-10-21-state-generation-v02-results.md)。源码生成与任务评分分开：这里没有规划成功率、公式拟合成绩或S更新效果。

## 为什么改运行边界

旧第三请求超时且用量未知，停止规则正确触发。诊断核查了原档、服务器原始文件元数据及已安装SDK/LiteLLM/HTTPX源码。原第一、第三规划请求完全相同，一次成功、一次超时；旧配置为60秒，运行目录的第三请求到响应文件写入间隔约60.10秒。这个文件时间差只是补充线索，不能冒称当时已经记录单调时钟延迟。

更准确的结论是“客户端记录了一次超时，异常状态码为408”。LiteLLM的Timeout默认状态就是408，因此旧记录不能区分本地HTTPX超时与真正的服务端408，更不能据此断言服务过载或模型推理失败。详见[超时诊断](../analysis/2026-10-21-state-generation-timeout-diagnosis.md)。

本批把有效超时从60增至180秒，保持模型、温度、提示、8槽分配、8192输出上限、每槽一次请求及5元保守预算不变。同步HTTPX的标量timeout约束连接、读取等阶段，并非完整流程的严格总耗时上限。因此这是等待窗口调整和可观测性补充，不是已证明的服务故障修复。

## 为什么整批重新生成

旧轮两份源码已经被查看和讨论，旧协议也已结束。新批次不能把它们与后补源码拼成原先完整八槽。这里预先重新分配全部八槽，旧两份仅进入历史重复索引，不提供给模型，不根据它们的质量选择新结果。缺失、重复、错误都照录；只允许这一新批次，不能在中止后自动开更多批直到成功。

规划仍给Spanner公开动作契约和两个旧公开例题输入；符号仍只给匿名输入维数和函数接口。这样的公式是待检验假设，没有数据拟合就不是科学规律发现。全部新提交结束或中止后才冻结会话树并分析语法/重复，生成过程不按这些分析筛选。

## 新证据如何阅读

每槽新增`transport-request.json`和`transport-result.json`。前者记录实际入口的timeout、重试、流式字段及对应request文件哈希；后者绑定前者并记录本地单调耗时、返回或异常。仅保存允许字段，排除密钥、headers与任意异常文本。一槽第二次dispatch或已有收据会在provider调用前拒绝。

这些记录与请求、响应、SDK工具收据、实际源码共同进入源码冻结。它们增强可信运行器范围内的可追溯性，不提供供应商签名或独立时间戳认证。语法通过、入口正确和AST不同都不能替代执行正确性。

## 复核

在服务器项目目录使用原Python3.12.14环境；AST版本差异会导致哈希不同：

```bash
LITELLM_LOCAL_MODEL_COST_MAP=True .venv/bin/python -m unittest tests.test_state_generation_v02 tests.test_state_generation_transport tests.test_state_generation_v02_audit
.venv/bin/python scripts/analyze_state_generation_v02.py --run-dir artifacts/state-generation/2026-10-21/v02 --output tmp/state-generation-v02-recheck.json
```

测试使用假provider，不调用真实模型。离线审计只读冻结记录与源码，不执行候选或读取符号CSV。实际结果、测试数量、归档哈希与费用统一以本批结果和验收记录为准。
