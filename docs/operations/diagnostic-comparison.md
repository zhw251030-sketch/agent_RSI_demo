# 诊断反馈开发对照：做了什么、为什么这样做

更新：2026-10-20。实际执行代码：`c36af55d4b20cb624f1cdb49cb5010990ce1d599`。

**本轮已完成诊断模块、离线干预、服务器验证和一次真实对照尝试，但六组对照没有全部运行完。** 两个会话正常完成，规划 B 在三个候选评价后触发输入长度限制，其余三个会话按预定规则未启动。所有候选与缺失条件均保留；不能据此宣布某组方法更好。

## 1. 为什么这一步研究反馈，而不是直接扩大数据

上一轮模型已经能提交程序／公式并收到实测评价，但出现了具体问题：规划程序读取谓词参数次序错误，模型又把失败归因于尚未验证的搜索问题；符号训练误差下降后，模型给出了超出已有分数支持范围的物理解释。

如果此时直接扩大任务或增加生成次数，很难分清成功是来自更多尝试、更详细的信息，还是更可靠的修订规则。本轮先拆开这三个因素中的后两个：

| 条件 | 反馈 | 修订规则 | 想观察什么 |
|---|---|---|---|
| A | 原有执行状态、异常位置和开发分数 | 普通修订提示 | 参照行为 |
| B | A 加执行诊断／残差统计 | 与 A 相同 | 增加诊断信息后的变化 |
| C | 与 B 相同的诊断生成规则 | 要求观测、假说、可证伪预测、证据检查及修改 | 在相同信息来源上改变修订规则的增量 |

三组使用相同模型、弱起点、候选上限和请求上限。所有组实际计算诊断，A 只隐藏模型可见的诊断内容。相同初始产物的诊断哈希已核对一致；后续程序不同，观测值自然不同，不能称为三条完全相同的反馈轨迹。

正式出处和近邻见[文献核查](../research/2026-10-20-diagnostic-feedback-neighbors.md)：CRITIC、Self-Debugging、llm-genplan、Reflexion 和 LLM-SR 已经覆盖工具反馈、自调试或候选迭代。本轮借鉴的是这些可核查的设计与消融思路，**没有声称“反馈后修订”是新方法，也没有声称完整复现了原论文**。

## 2. 两个任务各增加了什么反馈

规划继续使用 llm-genplan 的 Spanner，模型写完整 `get_plan(objects, init, goal)` 程序，在两道公开 prompt 和八道开发题上评价。新的详细诊断只对两道公开 prompt 开启：

- [planning_diagnostics.py](../../rsi_eval/planning_diagnostics.py) 在外层重放计划，给出已执行动作数、首个失败动作、缺失动作前提和未完成目标。最终成绩仍由 VAL 决定；二者判定不一致时作为设施错误处理。
- [planning_trace.py](../../rsi_eval/planning_trace.py) 记录候选源码行命中和函数调用／返回事件摘要，帮助区分“没有读到状态”“找不到路线”“搜索上限耗尽”等行为。它不记录局部变量值，最多 20,000 事件和 128 个行／函数条目；超过字节预算则明确报告不可用。
- 轨迹来自候选进程，可能不完整或被干扰，不能用未命中的代码行自动证明没有执行，更不能取代可信评分。生成器挂起也可能产生返回事件，文档和反馈均保留解释限制。

符号侧继续使用 LLM-SR 原论文公开 oscillator1 的 train，模型写 `equation(x, v, params)`，外层拟合参数并在新的隔离进程预测。新模块 [symbolic_diagnostics.py](../../rsi_eval/symbolic_diagnostics.py) 在可信外层计算残差 `预测值−观测值`：总体偏差、RMSE、标准化偏差，以及 x／v 固定四分位分箱中的数量、平均残差和 RMSE。

例如，“最高速度区间的 RMSE 更大”允许提出一个值得检验的结构假说，但不能直接推出“真实方程必有速度平方项”。同时，平均残差和 RMSE 是不同信息：均值接近零仍可能有较大波动。反馈只含聚合量，不包含原始样本行或真实方程。

统一接入点是 [executor.py](../../rsi_eval/executor.py)。每份诊断绑定任务、源码 SHA-256、范围和版本。旧接口默认不打开诊断；新对照由 [diagnostic_controller.py](../../rsi_eval/diagnostic_controller.py) 控制 A 隐藏、B/C 展示以及原有成绩选择规则。

## 3. 先用人工局部干预核对旧错误

[check_diagnostic_observations.py](../../scripts/check_diagnostic_observations.py) 对旧 planning-002／003 各做三种重放：原件、只修正 `at` 索引、再修正 `carrying` 索引。原件未改写，变体有来源哈希和逐行 diff。它们是**人工诊断干预，不是 Agent 新生成成果**。

| 旧候选 | 原件 | 只修 at | 再修 carrying |
|---|---:|---:|---:|
| planning-002 | 0/10 | 0/10 | 0/10 |
| planning-003 | 0/10 | 0/10 | 0/10 |
| 既有手写验收程序 | 10/10 | 不适用 | 不适用 |

“成绩仍为零”不表示修补毫无作用。002 原件在公开题仅处理一个状态，修补后处理更多状态，但仍有携带工具枚举缺口；003 修补后实际走过五步，再因找不到所选工具的路线退出，外层把部分计划丢弃。索引错误存在，但修正它不足以解决任务。

旧符号候选的重放复现了原训练成绩。最高速度四分位包含约 62.32%→55.59%→54.55% 的平方误差，支持误差集中现象；不支持直接认定某个缺失物理机制。详细观察、源码行和不确定性见[离线诊断分析](../analysis/2026-10-20-offline-diagnostic-probe.md)，原件／变体见[诊断产物](../../artifacts/diagnostic-probe/2026-10-20/README.md)。

该部分实际完成 70 次规划实例评价、3 次符号评价，模型调用 0，诊断／设施错误 0，封存测试 0。

## 4. 真实运行的全部结果，包括未启动条件

运行 ID：`20261020-diagnostic-comparison-v01`。MiniMax-M3，OpenHands SDK 1.55.1，工具仅 `submit_candidate` 和 `finish`。每个会话最多三个生成候选、四次模型请求；总上限 24 请求、10 元保守预留。三个策略在会话内固定，基础模型权重固定。

| 条件 | 生成候选的实测轨迹 | 最佳值 | 实际请求 | 状态 |
|---|---|---|---:|---|
| 规划 A | 0/10 → 0/10 → 10/10 | 10/10 | 4 | 正常结束 |
| 规划 B | 0/10 → 0/10 → 0/10 | 初始及候选均 0/10 | 3 | 评价后、下一请求发送前被输入上限阻止 |
| 规划 C | 未生成候选 | 不报告方法成绩 | 0 | 按停止规则未启动 |
| 符号 A | 未生成候选 | 不报告方法成绩 | 0 | 按停止规则未启动 |
| 符号 B | 未生成候选 | 不报告方法成绩 | 0 | 按停止规则未启动 |
| 符号 C | 0.09694021 → 0.09591726 → 0.09576767 | train NMSE 0.09576767 | 4 | 正常结束 |

规划初始空计划为 0/10，符号初始常数为 NMSE 1.0。未启动组虽然完成过初始执行检查，**这些初始分数不能充当该组运行后的成绩**。规划十题是同一程序的一批开发评价，不是十次独立方法重复；符号分数是训练拟合，不是测试结果。

规划 A 的第三个程序修正“只能携带一把扳手”的错误假设，实际使用集合记录多把工具并通过十题。规划 B 虽然得到更多诊断，却在第三版把有向通路擅自改成双向可达，与公开动作规则冲突。符号 C 使用了要求的证据格式，但仍出现把较小偏差称为主要剩余误差、把分箱误差波动解释为必需的速度非线性项等越界推断。

因此，本轮得到的更有价值的开发现象是：**提供证据和要求引用证据，并不足以保证模型正确使用证据。** 这是一组可审查的案例，不是已经证明普遍存在的机制效应。详细理由与反馈逐项核对见[真实轨迹分析](../analysis/2026-10-20-diagnostic-comparison-analysis.md)。

## 5. 为什么停止，以及花费如何记录

规划 B 第四次请求的完整序列化输入为 **98,376 字节**，比预设 **98,304 字节**上限多 **72 字节**。输入包含任务、工具定义、历史源码和反馈；即使单份诊断有界，历史累积仍会超限。

该大小来自无网络的真实 SDK 重放：使用已保存的三次模型响应和已保存的评价反馈，重建前三次输入并与原请求逐字节一致后，记录第四次输入。没有新增模型调用，没有再次执行候选；原始运行文件保持不变。重建证据随[核验记录](../environment/2026-10-20-diagnostic-comparison-verification.json)保存。

这不是供应商报错，也不是人民币额度用尽。预算检查在网络发送前拒绝请求；原运行只有 11 次实际请求，全部返回 usage。runner 按预先固定的错误停止规则没有启动后面三个条件。没有增加上限、重跑本轮或用补跑结果填补空缺。

| 本轮计量 | 数值 |
|---|---:|
| 实际网络请求 | 11 |
| 输入／输出 token | 104,661／14,428 |
| 已知 token 合计 | 119,089 |
| 按已配置标准单价估算 | 0.3409833 元 |
| 保守费用预留 | 1.4006853 元，未退还的预算计量，不是账单 |
| 未知 usage | 0 |
| 新增模型候选／固定初始副本 | 9／6 |

| 加上无模型预检和离线重放 | 规划 190、符号 12 |
| 封存测试／策略 S 更新 | 0／0 |

标准单价估算不等于供应商发票，缓存等账单项目另行核对。上一轮有一次未知使用量的失败请求，其账本仍保留，本轮不消除那笔历史不确定性。连接检查、旧小试和本轮的消费不能混为一个完整已知项目账单。

## 7. 验证与下一步

168 项不同测试通过：任务环境通过 151 项，17 项 SDK 测试在真实 1.55.1 环境通过。新 SDK 测试使用模拟传输，验证六种任务／条件的反馈实际进入工具消息、A 隐藏诊断、三候选上限和工具白名单，没有为测试额外调用模型。46 个运行源码／配置／提示哈希与服务器文件一致，56 个相关暂存验证文件与部署版本一致。

本轮仍未实现策略更新器，也没有完整 A/B/C 比较、新任务验证、显著性检验或成熟算法基线。C 是固定提示，不是自动因果验证系统；项目名 RSI 不应被写成已经完成的递归自我改进能力。

下一步先解决两项具体问题：把历史反馈压缩为有固定全会话预算、可回溯的诊断摘要，并保存精确拒绝原因；再针对“有向规则被改写”和“边际统计被升级为机制断言”等案例设计可执行的检查，而不是继续堆叠提示措辞。新版本通过无模型长度／边界测试后，再冻结新的完整对照。随后应在未参与提示设计的新父产物／任务上评价，检验机制作用，而不只展示当前最好的程序。
