# 冷启动源码生成、冻结与后续分配

本轮为后续策略比较准备新的程序和公式起点。代码、模型输入、请求预算与8个生成槽位先冻结，模型每槽只提交一次源码，全部尝试结束后才做静态分析。源码生成不包含任务执行、公式拟合、probe、策略 S 更新或模型权重更新。

本次真实轮在第3次请求收到 HTTP 408 / `LLMTimeoutError`，且该请求的 usage 未知，随后按协议停止。保存了2份源码，后5个槽位未启动；候选执行为0。Python 3.12 环境中的审计结论为 `record_consistent_incomplete`：已保存记录能够相互核对，但本次分配没有完成。具体源码、费用、归档位置和证据见[本轮结果](../analysis/2026-10-21-state-generation-results.md)。旧轮永久保留，不恢复、不补抽，也不能把失败请求的未知用量填成0。

## 为什么先生成并冻结起点

前几轮反复使用的 P-format、P-empty、S-v3、S-x5 已参与机制设计。它们适合解释检查器的行为，却不能靠增加重复调用变成独立验证。下一步需要把用于学习经验、决定是否接受策略和观察最终表现的材料分开，并在看到成绩前固定起点。

本轮采用模型冷启动生成：规划模型看到公开任务规则和两个公开例题输入，符号模型看到匿名函数接口；两者均看不到旧源码或旧成绩。提示要求认真求解，不故意植入错误。这样可以观察模型自然产生的起点，减少研究者按预期机制收益手工制造故障的影响。它仍不保证起点独立、困难、正确或有改进空间；模型可能输出相同模板、不可运行程序或已经足够好的程序。重复、缺失和错误都必须保留，不能根据结果补抽。

本轮解决的是来源和分配问题。只有后续对冻结起点进行真实评价，才知道它们是否正确，以及候选修订有没有收益；只有比较不同策略在相同起点上的配对终稿，才可能判断策略更新是否有用。

## 模型看见什么

8个宿主槽位中，规划有2个选择起点、2个评价起点；符号有2个 oscillator2 选择起点，以及 bactgrow、stressstrain 各1个评价起点。角色、槽位 ID、实际任务 ID、数据哈希都保留在宿主分配中，不写入模型任务包。

规划四槽共用完全相同的信息：Spanner 的公开动作契约和 seed0/problem0、problem1 的两个公开输入。符号输入只包含 `u0…uN`、维数、数组接口、通用算子约束和参数拟合约定，没有方程名、物理描述、原始列名、CSV数值行、统计量或参考式；相同维数的请求完全相同。实际 SDK 请求会再次核对，不能仅凭提示模板宣称输入公平。

匿名符号接口减少了方程名称和物理描述对初始表达式的直接提示，便于区分“提出初始假设”和“依据数据修订”。代价是模型没有数值证据，可能生成通用多项式或不适合任务的形式；输入维数本身仍带有先验，也无法据此排除预训练记忆。这样的初始表达式不能称为发现了规律，更不能称为恢复了真实方程。本轮不读取符号 CSV，也不拟合参数。

## 哪些记录说明发生了什么

一个完整运行目录采用以下关系：

| 记录 | 表示什么 |
|---|---|
| `runtime-freeze.json`、`input-freeze.json`、`generation-settings.json`、`history-index.json` | 首次请求前固定的实现、8槽任务包、模型设置和历史源码索引 |
| `budget-ledger.json` | 每次请求的事前预留、实际可知 usage、未知用量和停止状态 |
| `sessions/<slot>/requests/*.request.json`、`*.response.json`、`input-audit-0001.json` | 实际发送的完整请求、保存的原始响应及网络前后输入审计；失败时不伪造响应 |
| `sessions/<slot>/sdk-submission.json` | SDK确实分派的业务字段，先于核心提交写入；它本身不证明核心已接受 |
| `sessions/<slot>/source.py`、`candidate.json` | 核心已保存的源码字节及其身份，不代表运行成功 |
| `source-freeze.json` | 全部已开始会话的文件哈希与逐槽状态；包含停止轮已保存的前缀 |
| `static-analysis.json`、`summary.json` | 源码冻结后的静态信息与运行摘要，不含性能成绩 |

如果运行文件或冻结输入发生变化，运行器只能保存不可信快照，状态为 `integrity_failed`；它不能继续出具可信源码冻结。基础设施错误或未知 usage 触发停止后，未开始槽位保持未开始，缺失源码保持缺失。已知 usage 的无提交或业务格式拒绝会消耗该槽，但不能靠额外调用补成一份源码。

静态分析检查是否能被 Python 解析、入口签名是否符合接口，以及源码字节和 AST 是否重复。AST相同会忽略注释、排版和源码位置；当前比较不做变量重命名等价或语义证明。AST不同不代表算法不同，入口匹配不代表程序可运行。若存在跨角色的相同源码或AST，后续最多据实报告新任务实例上的行为，不能称为新程序起点泛化。

AST哈希依赖 Python 的 AST 表示。本轮运行与可信复核使用项目 `.venv` 的 Python 3.12.14；系统 Python 3.10 曾因历史 AST 哈希不同被审计器拒绝。不能因此重写旧哈希或把两种解释器的结果混用。

## 学习、选择与评价怎么隔开

| 阶段 | 规划数据 | 符号数据 | 作用 |
|---|---|---|---|
| 学习/组件开发 | 既有 seed0 的公开与开发材料 | oscillator1 的归档开发材料 | 从已知经验提出新策略 S1 |
| 策略选择 | seed1–2 去重后19题 | oscillator2 的 train | 比较 S0、S1 在同一起点上的终稿，决定接受或保留 |
| 后续评价 | seed3–9 去重后63题 | bactgrow、stressstrain 的 train | 评价已经冻结的策略 S*，成绩不回流到同次策略选择 |
| 继续封存 | 300道官方测试题 | 四方程的 test_id/test_ood | 本轮和这份后续分配均不启用 |

规划修订可见的反馈仍限于 seed0；19题和63题只供宿主在各自阶段评分，不把它们的成绩回传给同次修订。符号后续允许在所属任务的 train 数据上建立该起点的拟合反馈；评价方程的基线评分、反馈构建与修订必须等 S* 冻结后才开始。

oscillator2 曾在安装验收中被手写公式评分，不能重新标成完全未见任务。Spanner 的文本去重也不排除结构同构。方程 train 拟合表现不等于独立预测表现；同一方程上的两个源码起点不是两个独立方程，63个规划实例也不是63次独立策略学习。

## 后续36次分配表示什么

首版沿用8条人工通用规则中有序选择4条的有限策略表示。规则库、S0和渲染器由研究者固定，模型负责从学习包提出规则选择与顺序；这不是模型自主发明全部规则，也不是完整 GEPA 复现或更新器自改写。

分配表固定2次策略提案重复。两次都从同一 S0 和同一学习包出发，彼此不继承，也不从中挑一个较好的提案汇报。每次提案对应最多18次请求：1次真实更新、1次 shadow 更新、4个选择起点×2策略臂，以及4个评价起点×2策略臂。shadow 输出仅归档，不进入固定策略、记忆或任何修订上下文。两个重复共36次，拟单独使用最多12元账本；加本轮8次生成上限共44次。相同请求数和输出上限不等于实际 token、费用或计算量完全相等，需要分别报告。

选择时须直接比较 S0 与 S1 在同一选择状态上的配对终稿，保留逐任务成功集合，不能用两臂分别相对起点的“改善次数”替代策略间比较。缺源、缺测量或不确定选择不能晋级。S1未通过时 S*=S0；此时评价两臂使用相同策略，随机输出差异不能被解释为策略更新收益。

`execution_ready: false` 是实现状态标记，表示完整学习包、更新与修订提示全文、新角色执行权限、真实测量投影和选择器适配尚待冻结与验收；它不是缺少用户授权，也不是要求重新征求继续工作的许可。本轮停止且起点批次未完整，因此这36槽当前不得启动。
