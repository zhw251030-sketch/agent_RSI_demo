## P-format：原承诺履行与重新声明给出相反结果

草稿声明 `apply_format_patch`，部署声明 `raw_validation`，但源码 SHA-256 与原程序相同：`954089736b47434d9f2a334a34856c6f4dc5e3b887d98fb48eb8dee2754897fc`。理由同时包含“保持原样”和“修复已经写入源码”等互相冲突的说法；正式编辑声明检查为矛盾，部署声明检查为支持。

自行复查终稿只把 `_fmt` 中

```python
return "(" + " " + " ".join([name] + list(params)) + ")"
```

改成

```python
return "(" + " ".join([name] + list(params)) + ")"
```

候选全 AST 与预先规定的有限格式补丁相同，原承诺和最终承诺均支持。公开 2/2、开发 8/8；这是相对历史原起点 0/10 的实测改善。草稿本轮没有执行，不能称为实测草稿 0→10。

checked 终稿仍是原源码，声明改为 `keep_bytes`。新声明支持，但按原 `apply_format_patch` 检查仍矛盾；`declaration_only_change=true`，`original_commitment_repaired=false`。结果公开 0/2、开发 0/8。它明确承认草稿没改，因此不再属于“误以为补丁已部署”的案例；问题转为接受保留失败程序的决定。

这是本轮唯一初始编辑矛盾，对应 self 真修复、checked 仅重声明。检查输出不是漏检或把成功补丁错判成失败：它正确指出草稿未改，而后续模型选择改声明。单对样本仍不能排除随机生成差异，不能据此证明检查必然造成保守退化。

## P-empty：字节误差与算法失败不能混合解释

两组共享草稿为原样源码，`keep_bytes` 支持，部署 `unspecified` 为未知。已存 probe 表明两个公开题中原计划为空，边缘空白清理不能修复。两组均拿到这一证据。

self 改成定向图最短路径加贪心取扳手/拧螺母方案，声明 `general_edit`。检查器无法为一般改写证明特定源码关系，因此为未知；候选仍照常执行，公开 0/2、开发 0/8。不能把未知等同于坏算法，但实测没有完成任务。

checked 表示保持原样，实际只删除源码末尾一个 LF，参数元数据不变，AST 不变。严格 `keep_bytes` 因字节不同而矛盾；这不是功能上改了规划逻辑，更不能说删除 LF 导致任务失败。终稿仍 0/10。原已通过的字节承诺在复查后变为矛盾，说明草稿检查正确也不保证终稿保持该性质。

该规划案例的 `n_params=3` 是历史载入的参数元数据，并不代表规划器有三个可拟合参数；没有据此对规划复杂度作研究结论。

checked 理由把该 probe 的 `contradicted` 解释成“does not support simplification”。实际被否定的是“删项损失超过 1e-5”，不是简化本身。self 则正确读出损失低于阈值，但仍以最终重新拟合尚未验证为由保留原式。两组都保守，但文字中的证据理解并不相同；不能把 checked 的误读归因于新增字节检查，也不能把 `keep_bytes` 支持当作整段理由正确。原文见 [self 提交](../../artifacts/edit-commitment/2026-10-21/v01/reviews/S-x5-self/final-commitment.json)与[checked 提交](../../artifacts/edit-commitment/2026-10-21/v01/reviews/S-x5-checked/final-commitment.json)。
