## 4. 第七请求为什么停止

失败位置为 `r1-selection-S-select-1-updated`。原始响应包含一个 choice，结束原因 `tool_calls`，两个函数调用依次是 `submit_candidate`、`finish`。只有一个业务候选提交，两者携带的 SDK 元数据都合法。实际请求也公布了这两个工具，`tool_choice=null`；提示要求提交候选一次，但未明确禁止随后附带 finish。

[pilot_agent.py](../../rsi_eval/pilot_agent.py) 的原始响应守卫要求总工具调用数恰好为 1，在 SDK 派发和业务接受之前抛出 `PilotResponseContractError`。因此本次暴露的是单步协议与 SDK 默认结束工具的另一处不一致，不能说成上次元数据修复失效、模型超时或符号性能失败。该请求约 9.50 秒返回，usage 已知；响应里的符号源码没有被接受、执行或评分。

只读诊断用实际 SDK、阻断网络，做了两个隔离回放：原样双调用重现错误；只在模拟副本中移除末尾 finish，保留候选参数原字节，得到模拟接受。两次序列化请求均与真实第七请求逐字节相同。模拟候选未执行，复制的 usage 不入研究账本，不能补成真实第七次成功。

另一次不调用 provider 的接口捕获验证：SDK 1.55.1 支持 `include_default_tools=[]`，可以只公布业务提交工具。**此方案仅诊断验证，尚未修改生产实现。** 简单将数量限制放宽到 2 并不足够：还需调用顺序、身份、元数据和原子接受/审计，且 SDK 遇到 finish 会截断其后调用。

证据：[完整离线诊断](../../artifacts/strategy-measured/2026-10-21/v02/diagnosis/README.md)。

## 5. 提案解释仍须核对

这些核对是本轮归档分析，不是新反馈干预或已验证改进机制；未将本次解释、失败或评价信息追加进冻结学习包。
