# 最终 holdout 失败案例审计

日期：2026-10-26  
范围：`2026-10-25-final-v01` holdout 与两轮冻结开发记录  
目的：解释 OOD 上仍被部署的有害候选，判断问题来自 gate 误判、结构执行错误，还是开发证据向 OOD 迁移失败。

## 审计方法

按 `proposal_id` 将最终 holdout 的 `replacement_check` 行与两轮开发 `round-summary.json` 中的 `evidence` 和候选结构连接。只做事后分析，不改变已冻结的 gate action、阈值、候选或权重。开发证据的三个核心量为：

- `I-`：删除父结构中的特征后造成的 `deletion_loss`；
- `I+`：加入候选特征后的 `restoration_gain`；
- `R=I+/I-`：替换恢复比例，`supported` 的预登记条件是 `I- > 1e-8`、`I+ > 1e-5`、`R >= 1`。

## 主要发现

最终 OOD 中 `replacement_check` 的 4 个有害部署全部来自开发阶段 `supported`，没有一个来自 `contradicted` 或 `unknown`：

| proposal | 结构替换 | 开发证据（I- / I+ / R） | ID ΔNMSE | OOD ΔNMSE | 解释 |
|---|---|---:|---:|---:|---|
| `bactgrow-p02-r2` | `m_1_0_0_0 → m_0_0_1_0` | 0.009388 / 0.128459 / 13.684 | -0.113481 | +0.120225 | 开发与 ID 均改善，OOD 退化 |
| `stressstrain-p03-r1` | `m_0_2 → m_1_1` | 0.038260 / 0.079560 / 2.079 | -0.029118 | +0.168057 | 两次重复结果一致，OOD 均退化 |
| `stressstrain-p03-r2` | `m_0_2 → m_1_1` | 0.038260 / 0.079560 / 2.079 | -0.029118 | +0.168057 | 与上一槽位同一父/候选结构 |
| `oscillator2-p01-r2` | `m_1_0_0 → m_0_0_2` | 0.001466 / 0.003490 / 2.381 | -0.002399 | +0.013170 | 开发收益较小，OOD 方向翻转 |

这里的 `ΔNMSE` 定义为候选减父结构；正值表示候选退化。四个案例的 gate 判定本身与冻结协议一致，因此当前证据不能支持“实现错误”这一解释。更准确的说法是：替换充分性证据在开发域成立，但没有携带足够的分布支持信息，无法保证在 OOD 域仍成立。

## gate 状态与 holdout 结果的关系

按 24 个 proposal 的 OOD 结果统计：

| 开发 gate 状态 | proposal 数 | OOD 有害 | OOD 有利 | replacement_check 行为 |
|---|---:|---:|---:|---|
| `supported` | 8 | 4 | 4 | 8 个全部执行候选 |
| `contradicted` | 8 | 4 | 4 | 8 个全部保留父结构，拦截 4 个有害，但放弃 4 个潜在收益 |
| `unknown` | 8 | 1 | 1 | 8 个全部保留父结构，拦截 1 个有害，但放弃 1 个潜在收益 |

ID 上，8 个 `supported` proposal 全部有利，8 个 `contradicted` 中 7 个有害且全部被拦截；因此当前机制在 ID 上表现很好，但该结果不能外推到 OOD。OOD 上 `supported` 的有害率为 4/8，表明主要失败模式是“supported→OOD false positive”。

## 分布漂移证据

### `stressstrain`

开发切分中的 `temp` 覆盖约 0.0667–1.0，均值约 0.54；`test_ood` 的 `temp` 恒为 0.6667。更明显的是，OOD 的 `stress` 范围收窄到约 0–0.621，标准差约 0.126，而 `test_id` 的范围接近 0–0.911，标准差约 0.273。也就是说，OOD 不是简单的随机重采样，而是固定温度并改变响应范围。`m_0_2 → m_1_1` 在开发数据上恢复充分，可能依赖开发域中温度与应变的联合变化；当温度固定时，这个替换关系不再可靠。

### `oscillator2`

开发数据的时间范围约为 30–50，`x`、`v`、`a` 的范围分别约为 `[-0.206,0.175]`、`[-0.339,0.362]`、`[-0.711,0.660]`；`test_ood` 的时间范围变为 0–20，三者范围扩展到约 `[-0.403,0.535]`、`[-1.016,0.881]`、`[-3.547,1.908]`。因此 `m_1_0_0 → m_0_0_2` 的开发收益是在晚时间段、窄状态域上得到的，OOD 将系统外推到更早时间和更大振幅，导致小幅开发收益翻转为退化。

## 对机制的含义

这次审计把研究问题进一步收窄为“证据如何携带适用域信息”。当前 gate 只检查替换在 `check_dev` 上是否恢复删除损失，没有检查待部署数据是否仍处于证据支持域。因此它能够阻止开发域中明显被证据否定的候选，却不能识别开发证据在 OOD 上失效的候选。

下一版机制不应直接用本轮 holdout 调阈值。更合理的开发方向是：在新的开发切分上加入输入/目标支持度或分布漂移状态，把 `supported` 拆成“supported-in-domain”和“supported-under-shift”，并预先规定发生 shift 时是否保留父结构。新机制完成后再使用未参与设计的新 holdout 验证。当前四个失败 proposal 只能作为机制假设和下一轮开发设计的依据，不能作为调参样本。
