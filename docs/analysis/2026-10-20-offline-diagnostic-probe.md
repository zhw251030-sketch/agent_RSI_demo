## 3. planning-002：原始失败并非节点上限，修补后仍有动作枚举缺口

源码定位使用 [planning-002.py](../../artifacts/pilot/2026-10-20/planning-002.py) 的行号；两种补丁只替换索引，不改变行号。对应派生源码保存在 `sources/planning-002-at_only.py` 和 `sources/planning-002-at_and_carrying.py`。

### 3.1 实际观测

| 观测字段，problem0／problem1 | 原件 P002-O | 仅 at：P002-A | at + carrying：P002-AC |
|---|---:|---:|---:|
| 轨迹事件数 | 184／184 | 2860／2614 | 4516／4478 |
| `successors` 调用数 | 1／1 | 23／21 | 44／42 |
| `_man_location` 返回字符串次数 | 0／0 | 23／21 | 44／42 |
| `_man_location` 返回 None 次数 | 1／1 | 0／0 | 0／0 |
| `_carried_spanner` 返回字符串次数 | 未调用 | 0／0 | 38／36 |
| `_carried_spanner` 返回 None 次数 | 未调用 | 23／21 | 6／6 |
| 拧紧动作构造行 71 命中数 | 0／0 | 0／0 | 21／21 |
| 节点上限返回行 81 命中数 | 0／0 | 0／0 | 0／0 |
| 循环结束返回行 92 命中数 | 1／1 | 1／1 | 1／1 |

这些 helper 和 `successors` 的 `exception_events` 均为 0。由于此源码每弹出一个状态后调用一次 `successors`，且行 79 的 `nodes += 1` 命中数分别与 1、23/21、44/42 相同，可以将这些数解释为本次公开题中记录到的状态处理次数。它们与“达到 300000 个节点后中止”的旧解释直接不符。

只修 `at` 后，位置 helper 的返回类型从 None 改为字符串，后继列表最大长度从 0 变为 3；随后 carrying helper 的错误成为可见阻碍。再修 carrying 后，已记录到 21 次拧紧动作的构造，但函数最终仍从循环末尾返回空列表。**这些是搜索内部候选动作的构造，不是返回给 VAL 的实际计划已执行了 21 个动作。** 可信重放的执行动作数仍为 0。

### 3.2 为什么两处索引修复不足

静态检查可确认另一处语义缺口：修正后的 `_carried_spanner`（第 13–17 行）仍只返回状态集合中遇到的第一条 `carrying` 对应扳手；它不枚举全部携带扳手，也不筛选 `useable`。`successors` 第 62–71 行只对这一把扳手尝试拧紧。公开动作定义允许同时携带多把扳手，拧紧后仅删除 `useable`，不会删除 `carrying`；候选自身第 68 行也沿用了这一语义。

因此，当 helper 先遇到已使用的扳手、同时还携带另一把可用扳手时，第 63 行会跳过全部拧紧后继，漏掉本来合法的动作。即使被选中的扳手可用，也没有完整枚举其它可用扳手对应的动作。该程序依赖集合的迭代次序，不能由“两个参数顺序已正确”推出搜索转移关系完整。

**证据边界：这是源码可确认的动作枚举缺口，也是当前搜索耗尽的具体解释候选；不是已被本次干预单独证明的唯一原因。** 轨迹没有记录每个状态、扳手标识或局部变量，本次没有增加“枚举全部可用携带扳手”的第三类补丁。因此不能写成“已经证实只要再修这一处就能通过十题”，也不把集合迭代次序导致的潜在变化当成已完成的独立重复结果。

## 4. planning-003：位置恢复后暴露了“先到螺母，再找工具”的顺序问题

源码行号见 [planning-003.py](../../artifacts/pilot/2026-10-20/planning-003.py)，派生源码行号相同。

原件 P003-O 的两道公开题均为：`_man_at` 一次返回 None，`_bfs_route` 一次返回 None，`_construct` 一次返回 None；第 83 行命中，外层第 147 行返回空列表。这支持此前“位置接口错误使第一次寻路失败”的静态分析。

修复 `at` 后，P003-A 与 P003-AC 的两道公开题都记录到以下相同结构：

1. `_man_at` 返回字符串；第一次 `_bfs_route` 返回长度为 6 的列表。
2. `do_walk` 调用一次，第 68 行添加 walk 动作命中 5 次。源码随后把 `cur` 设为 `nut_loc`。
3. `_carrying` 调用一次并返回 None，没有异常。随后三次 `_bfs_route` 均返回 None；总计四次寻路，一次列表、三次 None。
4. 第 107 行尝试寻找扳手位置的路线命中 3 次；第 109、110 行选择可达扳手的分支均未命中。第 112 行 `return None` 命中一次。
5. 第 118 行拾取动作、第 132 行拧紧动作均未命中；外层第 147 行返回空列表。

这些记录与源码共同定位了一个具体失败分支：程序先规划到螺母位置，然后才寻找扳手，而当前两道公开题中三次向扳手位置的寻路都失败。公开[动作规则](../../prompts/pilot/planning.md)已规定 `link` 有向，去到目标后不能假设能返回沿途工具位置。这是“先决定到达目标，再补齐必要资源”的规划顺序缺陷。

本次不需要通过读取非公开题或未记录的局部变量来推断这个分支；判断直接来自第 81、84、107、112 行和函数返回摘要。此前静态诊断中关于 gate 终点与上游扳手的解释与此相容；本分析不把未收集的实际 `cur`／`sloc` 值写成轨迹直接观测。

继续修 carrying 次序没有改变上述失败分支，因为此时尚未成功拾取扳手。`_carrying` 返回 None 在这个阶段本身是合理结果；**不能仅凭出现 None 就再次认定 carrying 修补无效或函数有错。** 两版的总事件数略有不同（P003-A 为 507/501，P003-AC 为 533/503），不足以宣称算法发生了有意义的性能变化；状态容器是集合，扫描顺序与命中次数应和具体函数语义分开解释。

还需要区分内部构造与最终输出：五个 walk 动作先进入 `_construct` 的局部 `plan`，随后该函数返回 None，外层丢弃这一部分计划并返回空列表。因此“内部已经走了五步”不等于评价器执行了五步。原件的文档字符串虽写有 BFS fallback，主入口第 144–147 行只有构造失败后返回空列表；实际 `_bfs_route` 是位置之间的道路搜索，没有完整规划后备搜索。

### 5.1 哪些事实支持进一步检查速度相关结构

三候选最高速度箱的 RMSE 分别为 0.032472、0.030368、0.029565，均高于各自其它速度箱。因为各箱样本数相同，可由现有统计复核其平方误差份额：`n_bin * RMSE_bin**2 / (n_total * MSE_total)`，依次为 **62.32%、55.59%、54.55%**。25% 样本包含过半训练平方误差，支持“误差明显集中在该速度范围”的描述。

S002→S003 后，总体偏差更接近零，速度第二箱与第四箱的均值残差也更接近零；最高速度箱 RMSE 下降。这些现象与“加入当前速度非线性项有助于改善这批训练拟合”相容，是可继续检查的线索。

### 5.2 哪些事实限制了原来的强解释

首先，S001→S002 仅新增位置三次项时，最高速度箱 RMSE 已从 0.032472 降到 0.030368；变化发生在速度分箱中，不意味着新增项来自速度。x、v 及其它未纳入结构的因素可能共同变化，当前边际统计没有控制其它变量。

其次，S002→S003 并非每个区域都改善：最低速度箱 RMSE 从 0.014978 升至 0.015515，最高位置箱从 0.023223 升至 0.025654。所有已有参数也同时重新拟合；比较结果属于整个函数族与拟合过程的改变，不能把全部改善归给一个独立物理效应。

再者，“某速度区间的误差幅度大”与“残差均值的大部分变化可由速度解释”不同。为检查这一区别，可以仅由已保存聚合量计算一个**事后描述性分解**：

`R_bin = Σ_b n_b*(mean_residual_b - overall_bias)^2 / [n*(MSE - overall_bias^2)]`。

它表示当前四箱划分的箱间均值差异占中心化残差方差的比例；不是因果解释率、不是拟合另一个模型得到的独立 R²，也不是预先规定的新模型反馈。

| 候选 | x 四箱的 R_bin | v 四箱的 R_bin |
|---|---:|---:|
| S001 | 0.195% | 1.339% |
| S002 | 0.405% | 1.632% |
| S003 | 0.379% | 0.395% |

在粗分箱尺度上，速度箱均值差异只占很小一部分残差方差，其余差异仍位于箱内。这个结果限制了“已经观察到残差的大部分由速度箱均值结构解释”的说法；但粗分箱可能遮蔽箱内非线性，不能反过来证明速度没有重要作用。

因此，对上一轮“位置三次项收益很小，意味着残差由速度主导”的判断，应作如下更新：**速度最高四分位是值得检查的误差集中区域；当前新增速度项降低了训练误差与总体偏差；速度是否为主要缺失机制、是否优于其它结构解释，仍未被证实。** 不据此认定恢复真实方程，也不推导未见数据泛化。

## 6. 对下一步机制设计的具体含义

本次最直接的收获是，单一成绩可以掩盖不同的失败过程。002 的三个版本都是 0/10，但内部从“位置读不到”，发展到“可以搜索、不能用扳手”，再到“可以构造拧紧动作、搜索仍失败”。003 的相同成绩则对应第一次寻路失败和后续工具获取失败两个不同位置。若诊断只看最终 0 分，就可能重复提出已经失效的原因或错误地归因于计算预算。

后续证据约束提示可以要求模型把“局部预测是否兑现”和“完整任务是否解决”分别报告。例如，位置修补预测的是 helper 能正确取到位置、相关执行分支发生改变；它不自动预测十题全部通过。carrying 修补后仍返回 None，也必须先检查当前状态是否本来就未携带工具。符号侧则应将“误差在某范围集中”“新增函数项改善训练拟合”“某物理机制是原因”分成不同强度的命题。

本次只给这些规则提供了可审查实例，尚未证明规则会改善 Agent 表现。既有程序和本次人工补丁不进入新会话提示，安装验收程序也不作为模型参考答案。正式判断仍需预先划分未参与规则设计的新搜索状态与策略选择／最终评价范围，并有独立重复；本次十题不是十次机制实验，三公式也不是三个独立随机重复。

候选进程中的 Python 轨迹可能被候选干扰；即使本次没有截断或检测到中断，行命中及返回类型仍只是辅助审查证据，不能替代 VAL 或可信数值评分。本文关于控制流的解释结合了固定源码与实际轨迹；关于 002 剩余缺陷的充分性、符号缺失机制的身份，均保留未验证边界。
