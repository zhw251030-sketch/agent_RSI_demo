# 受控 Agent 开发小试协议 v0.1

日期：2026-10-20。此文件规定小试的输入、选择与证据边界，**不记录尚未发生的实验结果**。运行结果另存独立报告，并记录实际使用的代码、配置和提示哈希。

配置：[development-v0.1.json](../../configs/pilots/development-v0.1.json)。公开任务提示：[planning.md](../../prompts/pilot/planning.md)、[symbolic.md](../../prompts/pilot/symbolic.md)。

## 这一步要回答什么

两类任务执行器已通过离线验收。现在用固定 MiniMax-M3 和 OpenHands SDK，检查模型能否在有限预算内完成“阅读任务与父候选 → 提交修改 → 接收真实反馈 → 再修改或结束”的完整过程。小试用于发现接口、反馈、预算与候选修订中的具体问题。

本轮固定修订策略 `fixed-revision-v0.1`：检查证据、提出一个有理由的修改、执行、依据预定规则保留或退回。被修改的对象只有产物 P（程序或公式）；策略 S 不更新。两类任务复用这个流程，但模型会话、历史和产物完全分开，不向第二个会话传递第一个会话的经验。这是普通执行反馈修订的准备基线，尚不是 RSI 新机制或跨任务策略迁移实验。

## 两个独立会话与固定起点

| 会话 | 模型可见任务材料 | 固定初始产物 | 每个候选的评价 |
|---|---|---|---|
| 规划 | 公开域规则、typed tuple 接口、seed0 的 problem0/1 输入 | `fixtures/planning/empty_plan.py`，始终返回空列表 | 同一源码依序评价 2 个 prompt 与 8 个 development 实例 |
| 符号 | oscillator1 的 x、v、a 含义、函数接口、评价范围 | `fixtures/symbolic/constant.py`，1 个待拟合常数 | 仅官方 train：拟合参数、重新预测、外层算 MSE/NMSE |

起始产物内容及哈希在配置固定，由可信 runner 在首次模型请求前评价并附上源代码和真实反馈。空计划是故意不完整的起点；常数表达式是简单起点。这两个文件不是修订策略、参考解或成功样例。起始评价计入候选执行总量，单独标为 `initial`，不占最多三个模型提出候选的名额。

规划材料由 runner 调用现有 `prepare_task`，只提取清单标为 prompt 的两个任务并附加 JSON TaskView；worker 真正调用 `get_plan` 时传的是 `set[tuple]`。公开域中的动作名、参数顺序、前置条件和效果逐项保留。八个开发实例只提供逐题执行反馈，不额外向模型附上完整输入；本轮不提供语义失败的精确状态轨迹，不能将通用 `plan_semantics` 解释成已经定位了某条前置条件。

符号侧只选择 oscillator1，避免在首次连通性试跑中把候选预算分散到多个方程。它仍属于已经选定的符号发现路线，oscillator2 没有被取消。模型只接收任务说明及训练评分，不接收真实方程、数据路径、上游搜索记录、手写成功公式或原始样本行。参数拟合使用训练数据，当前反馈也来自同一训练数据；本轮不伪装成内部留出评价。

## 工具与候选记录

研究会话只配置受控 `submit_candidate(source, n_params, rationale)`，加 SDK 必需的会话控制工具；不配置 Terminal、文件读取、浏览器、网络搜索等工具。任务族、任务 ID、数据 split 和根目录由 runner 固定，模型不能通过工具参数更改。

`submit_candidate` 对规划执行固定十题批量，对符号执行固定一题训练评价。底层仍使用已有隔离执行与可信外层验证器。一次提交只能包含一个候选；模型必须看到其反馈后才能继续提交，不允许同一模型响应并行提交多个候选来绕过顺序与预算。

每次记录完整源码、哈希、编号、当前 incumbent 的 parent_id、固定 strategy_version、模型给出的 rationale、每题反馈、候选选择决定、模型使用量和执行量。rationale 是模型假说，与工具事实分开保存。所有失败、重复、未被选中和超时尝试均保留；重复源码不能借此重置候选额度。

## 预先固定的选择与报告规则

规划候选以八个 development 成功数为第一排序键、两个 prompt 成功数为第二排序键；完全相同时保留较早候选，初始候选也参与。基础设施失败不应当作程序能力分数，也不应触发凭空猜测的模型修复；记录该中断并终止或明确标记该会话无法完成评价。

符号候选以成功且有限的 train NMSE 从低到高排序；完全相同时保留较早候选。异常、拟合失败、超时或非有限分数不能替换成功 incumbent。NMSE 的分母是固定训练目标方差，因此同一数据上按 NMSE 和 MSE 排序一致；不能跨不同任务比较绝对 NMSE 后声称相同难度。

下一次修订的 parent_id 指向当前被选中的 incumbent。会话保留被拒绝候选及其反馈，但 runner 明确告知下一轮起点，不把最后生成和当前最佳混为一谈。

报告同时列出 `initial`、`first_generated`、`last_generated`、`best_development`，并列出全部候选轨迹和实际尝试次数。没有相应生成候选时填写 null，不以初始候选冒充模型输出。最佳分数受到开发选择影响，不作为独立泛化成绩；最后一次可能比最好一次差，这种情况同样报告。

本轮允许提前结束，例如规划十题均成功，或模型主动结束。每会话最多三个新候选，不能为了凑满数而无限追加请求。两会话是不同任务条件，不是同一方法的两个独立重复样本，不能据此计算有意义的方法显著性结论。

## 请求、执行与费用边界

配置中的小试上限为每会话 4 次模型请求、合计 8 次，单次最多 4096 输出 token；发送前序列化上下文最多 96 KiB。为整个小试预留最多 800000 个保守计量 token 与人民币 5 元，仍处在用户此前人民币 300 元的总预算内。实际实现必须在每次请求前执行预留检查，并单独保存供应商返回的实际 input/output/cache 使用量；这些预留数字不是实际消耗。

这里的“四次”包括可能用于结束总结的请求，也包括失败请求和重试的尝试计数。不能让 SDK 或底层客户端进行未计量自动重试。若请求使用量缺失、预算门槛不能验证或会话超限，应停止并标明原因，不能按零费用继续。

初始候选加三个生成候选的最大评价工作量为规划 40 个实例评价、符号 4 次拟合/预测评价。它与最多 8 次模型请求是不同单位，应分别报告；符号每次评价又包含拟合和预测两个受限进程。候选原有的时间、CPU、内存、输出限制继续生效。

预算字段是执行契约，由 runner 校验并在运行前保存配置哈希；若根据实际 SDK 计量方式调整，需在首次付费请求前一并更新配置和本段，不能在结果出来后追认预算。

## 数据边界与结论边界

- 保留规划官方测试与所有未选 seed 的封存边界；本轮不评分它们，也不据它们选择候选或停止时机。
- 符号不读取 test_id/test_ood 作为反馈，不宣称训练优化等于公式真值恢复。没有独立训练内选择集，因此只作开发小试。
- 只将白名单任务材料传给模型；原项目目录与 vendor 含成功样例或答案，不能作为 Agent 通用工作区暴露。
- 候选执行隔离和受控工具不同于普通 Canvas 会话。此次专用 SDK 会话的工具配置不能被描述成所有 Canvas 会话已经受限。
- 尚未比较固定策略与更新策略、尚未用新父候选检验策略迁移、尚未完成正式样本量与多任务评价。不得将这次运行直接写成“提出了通用 RSI 方法”。

下一步应基于真实候选轨迹检查是否出现可重复的错误或反馈不足，再设计同一起点、等预算的策略对照与独立评价。若这两个起步任务在极少尝试内就被稳定解决，应如实报告任务区分度不足，并扩展开发任务或制造明确、可审计的修订状态，不能用隐藏测试反复挑选难题。
